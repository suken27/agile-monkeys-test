This is a well-architected, thoroughly-documented DDD/CQRS project. I dug through the aggregate, command/query paths, persistence, outbox/queue infrastructure, and configs. Overall code quality is high — clean hexagonal boundaries, exhaustive sealed-error mapping, good test coverage (all unit tests passing). Here's what stood out.

Issues
1. Race condition on the "no duplicate in-flight promotion" invariant (JdbcPromotionRepository.java:73-83, Promotion.java:97-100)
The check is classic check-then-act: findActivePromotionsForTarget runs in one query, then save inserts, with no DB constraint tying them together. Two concurrent RequestPromotion calls for the same (applicationId, targetEnvironment) at default READ COMMITTED isolation can both pass the in-app check and both insert — the invariant SPECS.md calls out as domain-enforced is actually only enforced under non-concurrent load. Fix: a partial unique index (e.g. UNIQUE (application_id, target_environment) WHERE status NOT IN (...) — Postgres doesn't allow non-terminal-set predicates directly, but a generated "is_active" boolean column would work) or SELECT ... FOR UPDATE/SERIALIZABLE on the read.

2. README's quickstart doesn't actually work standalone (README.md:30-36)
./mvnw spring-boot:run is presented as sufficient, but there's no spring.datasource.* in application.yml — only env-var overrides used by docker-compose.yml. With spring-boot-starter-jdbc + the Postgres driver on the classpath and no URL configured, Boot can't find an embedded DB candidate and Flyway/JdbcTemplate startup will fail. The README should say to run docker-compose up -d postgres rabbitmq (or set the SPRING_DATASOURCE_* env vars) before spring-boot:run.

3. docker-compose.yml doesn't build from local source (docker-compose.yml:36-38)
Every service pulls ghcr.io/suken27/agile-monkeys-test:latest rather than build: .. SPECS §1.1's goal was "one-command-up" for local dev, but as written, local code changes are invisible until pushed and released through CI — you're always running whatever was last published to GHCR. Worth adding a build: block (or a separate docker-compose.override.yml) for local iteration.

4. No DLQ/retry policy on the RabbitMQ listeners (AuditLogListener.java, and the read-model/release-notes listeners)
Default Spring AMQP behavior on a handler exception is infinite nack-and-requeue. A single malformed/poison event (e.g. the ReadModelProjector's IllegalArgumentException on an unknown event type, or a missing promotion_detail row race) will loop forever and can starve the queue. Consider a dead-letter exchange + limited retry (spring.rabbitmq.listener.simple.retry).

Documented, known gaps (not bugs — already called out in README, worth reiterating priority)
Notification consumer (SPECS §8.3) has a port + in-memory adapter but nothing wired to call it on terminal events.
The AI release-notes agent, outbox relay, and read-model projector are all built but only activate under specific Spring profiles — easy to forget to run all of them together in docker-compose up (compose file does list them all, so this is fine there, just worth knowing for ad hoc local runs).
Nice things worth keeping
The aggregate (Promotion.java) genuinely owns every invariant; handlers are pure orchestration. ErrorMapping's exhaustive switch over the sealed DomainError hierarchy is a good touch — it fails the build instead of silently 500ing on a new error type.
Transactional outbox is implemented correctly (same-transaction insert, separate relay, at-least-once with idempotent consumers via ON CONFLICT).
Unit vs. integration test split (*Test vs *IT, Surefire vs Failsafe) is clean and well-documented.
Want me to fix any of these — the race condition and the README quickstart gap are the two I'd prioritize?

package org.springframework.amqp.rabbit.annotation;

import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

import org.springframework.core.annotation.AliasFor;

/**
 * A queue definition used within the bindings attribute of a {@code QueueBinding}.
 *
 * @author Gary Russell
 * @since 1.5
 *
 */
@Target({})
@Retention(RetentionPolicy.RUNTIME)
public @interface Queue {

	/**
	 * @return the queue name or "" for a generated queue name (default).
	 */
	@AliasFor("name")
	String value() default "";

	/**
	 * @return the queue name or "" for a generated queue name (default).
	 * @since 2.0
	 */
	@AliasFor("value")
	String name() default "";

	/**
	 * Specifies if this queue should be durable.
	 * By default if queue name is provided it is durable.
	 * @return true if the queue is to be declared as durable.
	 * @see org.springframework.amqp.core.Queue#isDurable()
	 */
	String durable() default "";

	/**
	 * Specifies if this queue should be exclusive.
	 * By default if queue name is provided it is not exclusive.
	 * @return true if the queue is to be declared as exclusive.
	 * @see org.springframework.amqp.core.Queue#isExclusive()
	 */
	String exclusive() default "";

	/**
	 * Specifies if this queue should be auto deleted when not used.
	 * By default if queue name is provided it is not auto-deleted.
	 * @return true if the queue is to be declared as auto-delete.
	 * @see org.springframework.amqp.core.Queue#isAutoDelete()
	 */
	String autoDelete() default "";

	/**
	 * @return true if the declaration exceptions should be ignored.
	 * @since 1.6
	 */
	String ignoreDeclarationExceptions() default "false";

	/**
	 * @return the arguments to apply when declaring this queue.
	 * @since 1.6
	 */
	Argument[] arguments() default {};

	/**
	 * @return true if the admin(s), if present, should declare this component.
	 * @since 2.1
	 */
	String declare() default "true";

	/**
	 * Return a list of admin bean names that should declare this component.
	 * By default all admins will declare it
	 * @return the bean names
	 * @since 2.1
	 */
	String[] admins() default {};

}

package org.springframework.amqp.rabbit.annotation;

import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

/**
 * Represents an argument used when declaring queues etc within a
 * {@code QueueBinding}.
 *
 * @author Gary Russell
 * @since 1.6
 *
 */
@Target({})
@Retention(RetentionPolicy.RUNTIME)
public @interface Argument {

	/**
	 * Return the argument name.
	 * @return the argument name.
	 */
	String name();

	/**
	 * The argument value, an empty string is translated to {@code null} for example
	 * to represent a present header test for a headers exchange.
	 * @return the argument value.
	 */
	String value() default "";

	/**
	 * Return the argument value.
	 * @return the type of the argument value.
	 */
	String type() default "java.lang.String";

}

-- Backstops invariant #2 ("no duplicate in-flight promotion per (application, target
-- environment)") at the database level. PromotionCommandService already performs a
-- check-then-act (SELECT active promotions, then decide, then INSERT) at the application
-- layer, but that is not atomic under concurrent requests: two requests for the same
-- (application, target environment) pair can both pass the application-level check before
-- either commits. This partial unique index makes the second concurrent INSERT fail instead
-- of silently creating two non-terminal promotions for the same target.
CREATE UNIQUE INDEX uq_promotions_active_target ON promotions (application_id, target_environment)
WHERE status NOT IN ('COMPLETED', 'ROLLED_BACK', 'CANCELLED');

package com.releasepilot.infrastructure.persistence;

import org.flywaydb.core.Flyway;
import org.springframework.beans.factory.InitializingBean;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import javax.sql.DataSource;

/**
 * Runs the {@code db/migration} Flyway migrations against {@link DataSource} at startup.
 *
 * <p>This is written out explicitly rather than relying on Spring Boot's own Flyway
 * auto-configuration because, as of the Spring Boot version this project builds against,
 * {@code spring-boot-autoconfigure} no longer bundles a {@code FlywayAutoConfiguration} class —
 * adding {@code flyway-core}/{@code flyway-database-postgresql} to the classpath alone does not
 * migrate anything. Without this bean, every {@code JdbcTemplate} query against the write or
 * read-model tables fails with "relation ... does not exist", since the schema is never created.
 *
 * <p>Safe to run unconditionally from every profile (the API and every consumer process): Flyway
 * takes a database-level lock for the duration of {@code migrate()}, so concurrent callers at
 * startup serialize instead of racing, and every call after the first is a no-op once the schema
 * history table shows nothing pending.
 */
@Configuration
public class FlywayMigrationConfig {

	@Bean
	public InitializingBean flywayMigration(DataSource dataSource) {
		return () -> Flyway.configure().dataSource(dataSource).load().migrate();
	}
}

All four issues are fixed and verified (unit tests, Testcontainers integration tests, and a live docker compose smoke test all pass). No commits made — these are working-tree changes for you to review.

What changed
1. Race condition on duplicate in-flight promotions — added V6__add_unique_index_on_active_promotion_target.sql, a partial unique index on (application_id, target_environment) for non-terminal rows. JdbcPromotionRepository.save() now catches the resulting DuplicateKeyException and rethrows DuplicatePromotionInProgressError, so the domain error surfaces even when two requests race past the application-level check. Added a new IT test that proves it (savingASecondConcurrentlyRequestedPromotionForTheSameTargetViolatesTheUniqueIndex), and confirmed live via curl: second concurrent request now gets a clean 409.

2. README quickstart — added the missing Postgres/RabbitMQ prerequisite and a "Running with Docker Compose" section.

3. docker-compose.yml didn't build from source — added build: (via a YAML anchor) to all five app-derived services and changed pull_policy to missing, so docker compose up --build now builds and runs your local code instead of always pulling ghcr.io/suken27/...:latest.

4. No RabbitMQ retry/DLQ policy — added spring.rabbitmq.listener.simple.retry (5 attempts, exponential backoff, capped at 30s) plus a dead-letter exchange/queue per consumer (audit-log, read-model-projector, release-notes-agent), so a poison message retries with backoff and then lands in a .dlq queue instead of looping forever or vanishing.

A 5th, more serious issue I found while verifying #3/#4
Smoke-testing via docker compose up --build (needed to validate the DLQ wiring against a real broker) surfaced that Flyway never actually runs. I confirmed by inspecting the jars directly: spring-boot-autoconfigure-4.0.7.jar contains zero Flyway classes, and neither flyway-core nor flyway-database-postgresql ships its own autoconfiguration — Spring Boot's Flyway auto-configuration doesn't exist in this version combination. Every request that touched the database was failing with relation "promotions" does not exist. This was invisible to the entire test suite because the Testcontainers *IT tests all call Flyway.configure()...migrate() themselves directly (bypassing Spring), and ReleasePilotApplicationIT's only assertion is that the context loads — it never queries anything.

Fix: added FlywayMigrationConfig.java, an explicit InitializingBean that runs Flyway.configure().dataSource(dataSource).load().migrate() at startup. Verified live: all 6 migrations now apply on boot, and a full request → conflict-on-duplicate round trip works end to end against real Postgres.
