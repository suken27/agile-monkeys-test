Right now DataSourceAutoConfiguration is excluded directly in ReleasePilotApplication.java — that's an always-on, compile-time exclusion, so it would also block a real datasource in production once deployed via docker-compose.yml.

Recommendation: drop the exclusion from the @SpringBootApplication annotation, and instead scope it to tests only, using the fact that test resources shadow main resources on the classpath:

Remove exclude = DataSourceAutoConfiguration.class from ReleasePilotApplication — production picks up spring.datasource.* automatically from the SPRING_DATASOURCE_URL/USERNAME/PASSWORD env vars docker-compose already sets.
Add src/test/resources/application.yml with spring.autoconfigure.exclude: org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration, so @SpringBootTest (e.g. ReleasePilotApplicationTests) still boots without a live Postgres.
JdbcPromotionRepositoryIT is untouched by this either way since it builds its own HikariDataSource/Testcontainers instance and never loads the Spring context.

Tradeoff: it splits config across two resource files instead of one flag in code, but it's the standard Spring Boot idiom and means the test exclusion can never accidentally leak into the deployed app.
